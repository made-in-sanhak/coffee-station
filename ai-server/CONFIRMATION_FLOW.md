# 확인 흐름과 이후 개발 순서

## 구현 상태

Express `POST /api/recommendations/prepare`: message를 받아 조건 추출만 수행한다.
Python 내부 경로는 /recommendations/prepare. 반환값은 기존 success/data/message 형식이다.
data에는 proposal_id, proposal(원문 근거/미해결 조건), suggested_constraints, notice가 있다.
정렬 미지정 시 가격순, 표시 개수 20개를 제안하고 명시적으로 표시한다.
AWAITING_CONFIRMATION은 확인 가능, NEEDS_CLARIFICATION은 문장 수정 후 재추출이 필요하다.

Express `POST /api/recommendations/confirm`:
`{proposal_id, confirmed:true, constraints:{...사용자가 확인한 전체 조건...}}`.
부분 수정이 아니라 전체 교체 조건이다. 사용자는 가격/종류/정렬 등을 명시적으로 수정할 수 있다.
원래 문장 대신 확정 조건만 검색에 적용한다. 미해결 조건이 남은 제안은 409로 거절한다.
확인 거절/만료/중복도 409, 잘못된 조건 422. 확정 성공 후 기존 RESULT/QUESTION을 반환한다.
기존 /api/recommendations는 확정 조건을 직접 받는 내부 개발 경로로 유지한다.

제안 저장소는 단일 Python 프로세스 메모리, TTL 10분, 최대 100건, 임의 토큰 1회 사용이다.
검색 시작 시 토큰을 소비하므로 서비스 오류 후에는 새로 준비한다. 자동 재시도하지 않는다.
원문 전체를 저장하지 않으며 서버 재시작 시 제안이 사라진다.
아직 사용자 계정에 연결되지 않은 로컬 실습용이다. 다중 worker/외부 공개용이 아니다.
기존 내부 API 토큰 인증은 유지하며, 사용자 인증과 제안 소유권 검증은 다음 단계다.

노트북 7절에서 준비 셀 → 결과 검토/수정 → USER_CONFIRMED=True 순으로 실행한다.
2026-11-09 실제 Express/Gemini/데모 DB 검증: 준비 후 확인, 메뉴 3개 일치.
자동 테스트 60개 통과. 확인 전 검색 없음/수정 반영/만료/중복/미해결 차단 검증.

## 앞으로의 단계

1. React Native 확인 화면: 원문 근거, 편집 가능한 조건, 미해결 질문, 확인 버튼, 결과 표시.
2. 사용자 인증 및 제안 소유권: 요청 제한, 사용자별 상태, Redis 등 공유 저장소, 만료/중복 UX.
3. 후속 대화: 직전 추천 범위와 확정 조건 유지, '더 저렴하게' 및 조건 변경 동의.
4. 실제 선별 DB: 매장/메뉴 매핑과 영업·단맛·디카페인 등 확인 가능한 데이터 확장.
5. 개인화: 가입 취향/메뉴 평가/매장 리뷰 분리, 현재 요청 우선 규칙, 거리·가격·취향 점수 검증.
6. 배포 준비: Docker 서비스 통신, 비밀값, 로그/모니터링, 지연·비용·오류 평가.

한 단계씩 검증한다. 지금은 확인 흐름까지만 구현했으며 개인화 점수와 앱 UI는 아직 없다.
