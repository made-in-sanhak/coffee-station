# 행신 아메리카노·카페라떼 가격 자료

## 구성

1. `source/haengsin_final_prices_test.sql`: 제공 원본 그대로 보존.
2. `001_staging_schema.sql`: 검토용 영구 테이블 2개 생성.
3. `002_staging_seed.sql`: 원본 57개 가격 옵션과 매장명 8개 입력.
4. `003_inspect.sql`: 누락값·출처·매장별 옵션 조회.

사용자 승인 후 별도 coffee_station_haengsin_test DB에 적재하고 읽기 전용 검색을 검증했다. 기존 Agent/앱 추천 경로에는 아직 연결하지 않았다.
원본 바이트 일치, 가격 INSERT 본문 보존, 8개 매장 코드 대응을 정적으로 확인했다.
MySQL 실제 적재(8개 매장/57개 옵션)와 노트북 조회 검증을 완료했다. 상세 결과는 WORK_PLAN.md를 참고한다.

## 왜 별도 staging인가

원본은 TEMPORARY TABLE을 사용하므로 연결 종료 시 자료가 사라진다.
매장명은 SELECT 출력에만 있고 좌표·주소·내부 cafe_id는 없다.
운영 스키마와도 차이가 있어 바로 메뉴 가격에 넣지 않는다.

- HS001 등은 제공 자료의 코드이며 내부 cafe_id나 카카오 장소 ID가 아니다.
- 사이즈는 원문 그대로 보존한다. Short/Regular/기본 등을 임의로 같은 옵션으로 합치지 않는다.
- HOT/ICE는 명시적 컬럼으로 보존한다. 기존 menu_prices에는 전용 온도 컬럼이 없어 매핑 결정이 필요하다.
- price_basis/source_url을 보존한다. 기존 source의 짧은 코드 컬럼에 억지로 넣지 않는다.
- 원본에는 unverified 2행, 과거 사진·브랜드·배달 메뉴 등 다양한 근거가 있다.
  가격이 채워져 있다는 이유로 현재 매장 판매 가격으로 확정하지 않는다.
- 검증일은 제공되지 않아 verified_at=NULL로 둔다. 적재일을 검증일로 만들지 않는다.
- 가격 출처 URL은 이번에 외부 접속·사실 검증하지 않았다.

## 나중에 실행할 때

사용할 DB를 명시적으로 선택한 뒤 001 → 002 → 003 순서로 실행한다.
001은 기존 테이블이 있으면 실패하도록 구성해 덮어쓰지 않는다.
002는 신규 staging 테이블에 한 번 적용한다. 재실행용 upsert가 아니다.
오류 무시(--force)로 실행하지 않는다. 오류 발생 시 ROLLBACK 후 원인을 확인한다.
MySQL DDL은 트랜잭션으로 되돌릴 수 없으므로 부분 생성 상태를 확인한 뒤 재실행한다.
운영 cafes/menus/menu_prices를 변경하는 구문은 없다.

## 실제 서비스 연결 전 필요한 작업

1. 매장 주소·위도/경도·카카오 장소 식별자 확인.
2. store_code와 기존 cafes.cafe_id 매핑.
3. 아메리카노/카페라떼의 내부 menu_id와 브랜드별 상품명/옵션 매핑.
4. 판매 상태·가격 근거·검증일 확인. 미검증 가격을 기본 추천 후보로 넣지 않기.
5. 실제 스키마에 맞는 변환/적재 SQL 작성과 격리 테스트.
6. 사용자 승인 후 지도/추천 조회 연결.

임시 매장 좌표나 검증 날짜를 만들어 빈 값을 채우지 않았다.
행신 자료만 승인된 범위에서 테스트했다. 기존 모의 개발 기본 설정은 그대로 유지한다.
