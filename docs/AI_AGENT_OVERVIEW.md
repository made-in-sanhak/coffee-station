# Coffee Station AI Agent 개발 현황 및 팀 공유 자료

작성 기준: 2026-11-09

## 1. 프로젝트에서 AI가 담당하는 역할

Coffee Station은 위치·가격·취향·목적에 맞는 카페와 메뉴를 찾는 서비스다.
AI 기능은 **자연어 해석, 리뷰 요약, 메뉴·매장 추천**으로 구분한다.
대학교 Agent 수업에서 배운 도구 호출과 반복 실행을 실제 서비스에 적용하는 것도 개발 목적이다.

현재는 기능별 책임과 테스트 흐름을 구현한 프로토타입이다.
실제 서비스 데이터 기반 개인화 추천이나 운영 배포가 완료된 상태는 아니다.

## 2. 전체 구조

```text
React Native 앱
  └─ Express 백엔드: 앱 요청 수신, Python 호출, 공통 응답 처리
       └─ Python FastAPI 서비스
            ├─ 자연어 조건 추출: Gemini 또는 고정 응답 모의 모델
            ├─ 사용자 확인: 추출 조건 검토·수정·확정
            ├─ 직접 추천: Python 필터·정렬 (기본)
            ├─ Agent 추천: Gemini 도구 선택·반복 실행 (선택)
            ├─ Repository: 모의 JSON / MySQL 조회 구현 교체
            └─ 리뷰 요약: 모의 구조화 발췌와 로컬 저장·재사용
```

기존 Express를 Python으로 교체하지 않았다. 단일 저장소의 `ai-server/`를 독립 서비스로 사용한다.
MySQL은 Docker에서 실행하는 구조를 고려했다. 카카오 지도는 향후 앱에 연동할 예정이며 아직 구현하지 않았다.

## 3. 추천 요청의 처리 과정

예시 입력: **“4천 원 이하 커피를 저렴한 순으로 추천해줘.”**

1. 조건 추출: 최대 가격 4000원, 종류 COFFEE, 정렬 price.
2. 추출 근거 표시: “4천 원 이하”, “커피”, “저렴한 순”.
3. 사용자 확인: 조건을 그대로 승인하거나 가격·종류 등을 수정한다.
4. 확정 조건으로 조회: 예산을 넘는 메뉴는 제외하고 가격순으로 정렬한다.
5. 결과 표시: 가격·메뉴·매장 정보는 조회 데이터에서 구성한다.

조건이 없거나 모호할 때 임의로 가격·위치를 만들어내지 않는다.
단맛·디카페인·공부 목적처럼 현재 데이터/추출 구조에서 처리할 수 없는 조건은 미해결 항목으로 남긴다.
결과가 없을 때 예산을 자동으로 올리지 않고 사용자에게 변경 여부를 묻는다.
현재 미해결 조건을 해결하려면 문장을 수정해 다시 준비해야 하며, 자유로운 후속 대화는 아직 연결하지 않았다.

확인 제안은 단일 Python 프로세스 메모리에 최대 100개, 10분간 저장하며 1회 사용한다.
서버 재시작 시 사라지고, 확인 요청 실패 후에도 새로 준비해야 할 수 있다.

## 4. Agent 방식과 직접 추천 방식

### Agent 방식 — 학습 및 복잡한 도구 사용 실습

```text
요청 관찰 → Gemini의 도구 선택 → Python 도구 실행
        → 결과를 Gemini에 전달 → 추가 검색 또는 최종 응답
```

직접 구현한 반복문을 사용하며 LangGraph는 현재 사용하지 않는다.
도구는 `search_cafes`, `search_menus`, `get_cafe_details`다.
도구 인자와 필수 조건을 검증하고, 검색되지 않은 메뉴 ID를 최종 추천에 포함하지 못하도록 검사한다.
기본 제한은 모델 호출 6회, 도구 호출 10회, 실행 시간 예산 60초다.
이는 동기 DB 작업까지 강제 중단하는 엄격한 전체 요청 제한은 아니다.

### 직접 추천 방식 — 일반 서비스의 기본 경로

확정된 조건을 Python이 검색·정렬하고 결과를 반환한다. 이 단계는 LLM을 호출하지 않는다.
자연어 추출을 Gemini로 수행하면 정상적인 준비→확인 흐름은 보통 추출 1회 호출만 필요하다.
Agent 방식에서는 여기에 도구 선택·최종 처리 호출이 추가된다.

따라서 **Agent를 만들었다는 이유만으로 API 사용량이 줄어드는 것은 아니다.**
언어 해석과 계산을 분리해, 필요한 경우에만 LLM을 쓰도록 구성했다.

## 5. 수업 개념을 적용한 부분

| 개념 | 적용 내용 |
|---|---|
| Agent Loop | 관찰 → 결정 → 도구 실행 → 결과 관찰 반복 |
| Function Calling | Gemini가 선택한 도구와 인자를 Python에서 검증·실행 |
| Context Engineering | 시스템 지시, 확정 조건, 사용자 메시지, 최근 대화 분리 |
| ReAct 형태 도구 활용 | 도구 결과에 따라 다음 행동 선택; 내부 사고 과정 출력은 요구하지 않음 |
| State | 기본 대화 상태·직전 후보 목록·확인 제안 상태 관리 |
| Retrieval | 모의 카탈로그/MySQL의 구조화 데이터 검색; 벡터 RAG는 미구현 |
| Evaluation | 정답 메뉴 ID, 조건 위반, 빈 결과, 오류, 호출 횟수와 시간 검증 |

대화 상태 구조는 존재하지만 사용자 계정에 연결된 장기 대화 기능은 아직 아니다.

## 6. 리뷰 요약의 현재 범위

현재는 Gemini 종합 요약이 아니라 **고정 모의 문장의 분류와 원문 발췌**다.

- 리뷰 ID·원문 발췌·주제·긍정/부정/중립을 구조화한다.
- “평일에는 조용함”과 “주말에는 시끄러움”을 각각 보존한다.
- 근거 없는 리뷰 ID, 원문과 다른 인용, 중복 근거, 잘못된 출력 형식을 거절한다.
- 대상 리뷰 수, 실제 발췌 수, 근거 ID, 생성 시각과 생성기 버전을 저장한다.
- 동일 입력은 SQLite 저장 결과를 재사용하고 수정·삭제·숨김 변경 시 갱신한다.

주제·감성의 의미적 정확성까지 자동 증명하는 것은 아니다.
리뷰 의견은 검증된 매장 사실이 아니며 현재 추천 점수에도 사용하지 않는다.
제공 ERD의 reviews에는 메뉴 연결 필드가 없어, 현재 조회 설계는 매장 리뷰 기준이다.
실제 리뷰 조회 구현은 준비했지만 실제 DB 리뷰에 연결해 검증하지 않았다.

## 7. 데이터 모드와 개발 원칙

**일반 개발은 모의 데이터만 사용한다. 행신 SQL은 사용자 요청으로 별도 테스트 DB 사용을 승인받았다. 다른 실제 데이터는 추가 승인 전까지 사용하지 않는다.**
현재는 외부 API 장애나 무료 티어 제한과 무관하게 개발할 수 있도록 모의 모드를 제공한다.

| 설정 | 값 | 역할 |
|---|---|---|
| EXTRACTION_MODE | mock / gemini | 고정 문장 추출 실습 / 실제 자연어 추출 |
| RECOMMENDATION_MODE | direct / agent | Python 직접 추천 / Gemini Agent Loop |
| AGENT_REPOSITORY | mock / mysql-demo / mysql | JSON 임시 자료 / 격리 데모 DB / 실제 DB 연결 준비 |

비용 없는 기본 개발 조합은 `mock + direct + mock`이다.
코드상 추출 기본값은 gemini이므로 서버 실행 시 EXTRACTION_MODE=mock을 명시해야 한다.
모의 모델은 임의의 자연어를 이해하지 않으며 등록되지 않은 문장은 확인 필요 상태로 처리한다.
외부 호출 실패 시 모의 결과로 자동 대체하지 않는다.

새 노트북:
- [모의 데이터 개발용](../ai-server/notebooks/mock_data_development.ipynb): 외부 API·DB 없이 실행.
- [실제 연결 준비용](../ai-server/notebooks/real_data_ready.ipynb): 승인된 행신 테스트 DB 조회용. 기본 RUN_HAENGSIN_TEST=False.

기존 통합 실습 노트북은 과거 실험 기록이며 일부 셀에서 실제 API/DB를 호출할 수 있다.
API 키·비밀번호는 환경 설정으로 관리한다. Git 관련 작업은 사용자 별도 지시 전까지 보류한다.

## 8. 구현한 API와 앱 화면

| Express API | 용도 |
|---|---|
| POST /api/recommendations/prepare | 조건 추출, 확인 제안 생성 |
| POST /api/recommendations/confirm | 사용자가 확인한 전체 조건으로 추천 |
| POST /api/recommendations | 확정 조건을 직접 전달하는 개발 경로 |
| GET /api/cafes/{id}/review-summary | 모의 매장 리뷰 요약 조회 |

Python 내부 API는 공유 토큰을 확인한다. 이 토큰을 앱에 넣지는 않는다.
실제 사용자 인증·제안 소유권 검증·요청 제한은 아직 남아 있다.
리뷰 조회는 설정과 무관하게 고정 모의 매장 990001/990002만 지원한다.

React Native에는 다음 화면을 구현했다.
1. 요청 입력·예시 불러오기
2. 추출 근거 표시, 예산·종류 수정, 명시적 확인
3. 추천 메뉴·가격·가상 매장 및 빈 결과 표시
4. 모의 리뷰 요약과 조회 상태 표시

기본 앱 실행은 네트워크 없는 로컬 샘플이며, 모의 서버 모드로 전환할 수 있다.
현재 추천 화면은 가격순이며 위치 입력·거리순 UI·지도는 아직 없다.
실제 에뮬레이터/휴대폰에서 레이아웃과 통신을 검증하는 작업도 남아 있다.

## 9. 검증 결과와 한계

- Python 자동 테스트: 최신 실행 기준 72개 통과.
- Express: 모의 Python 서버를 이용한 전달·오류 처리 테스트 통과.
- 프런트엔드: TypeScript·변경 파일 린트, 최신 Jest 7개 통과.
- 과거 실제 Gemini/데모 MySQL 통합: 조건 검색, 4000/3999/2999원 경계값, 빈 결과 처리 확인.
- 실제 Gemini 조건 추출: 예시 5개 통과. 이는 일반 한국어 정확도 보장이 아니다.
- 일반 기능은 모의 데이터로 검증. 사용자가 승인한 행신 가격 자료는 별도 MySQL 테스트 DB에서 검증했으며 Gemini는 호출하지 않았다.

일부 실행에서 Gemini 503/504를 경험했다. 무료 티어 소진으로 단정하지 않고
오류 종류를 구분해 전달하도록 했다. 일시 오류 자동 재시도는 아직 적용하지 않았다.
실제 데이터 품질·운영 부하·개인화 추천 효과는 검증 전이다.

## 10. 행신 DB 연결 완료 범위와 다음 통합 목표:

사용자 승인 후 `coffee_station_haengsin_test`에 매장 8개·가격 옵션 57개를 적재했다.
`app/repositories/haengsin.py`에서 메뉴·가격·HOT/ICE·사이즈·매장 코드 검색과 매장별 최저 옵션 비교를 제공한다.
노트북 실제 실행으로 4000원 이하 ICE 아메리카노 12옵션, 카페라떼 6옵션을 확인했다.
미검증 2행과 좌표 전체 누락도 확인했다. 기본 조회는 unverified/출처 누락을 제외하지만
나머지를 검증된 현재 판매 가격으로 확정하지 않는다.
이 경로는 가격 비교 전용이며 기존 추천 API/앱/지도에 아직 연결하지 않았다.
기존 업무 테이블은 변경하지 않았고 앱 계정에는 테스트 DB SELECT 권한을 부여했다.
상세: [행신 작업 계획](../backend/sql/haengsin/WORK_PLAN.md).

다음 통합 목표: 카카오 지도와 선별 메뉴 DB

초기 투입 메뉴는 **아메리카노와 카페라떼**로 한정할 계획이다.
카카오 API 기반 지도 화면과 연결해 다음 흐름을 로컬에서 검증한다.

```text
지도 표시 → 메뉴 조건 선택 → 해당 메뉴 판매 매장 표시
        → 매장/메뉴 추천 → 추천 결과 선택 → 지도에서 매장 확인
```

필요 데이터는 매장 ID·이름·주소·위도/경도, 메뉴 ID·이름·종류,
매장별 메뉴 가격·옵션·판매 상태다. 카페라떼는 현재 LATTE 카테고리로 구분한다.
COFFEE 카테고리 전체와 특정 메뉴인 아메리카노는 같은 의미가 아니므로,
지도용 조회에서 메뉴 ID 기반 선택 조건을 별도로 연결해야 한다.

지도 SDK가 메뉴 가격을 제공하는 것으로 가정하지 않는다.
지도는 위치 표시를 담당하고, 매장-메뉴-가격 관계는 프로젝트 DB에서 조회한다.
카카오 장소 정보와 내부 cafe_id의 연결 방식, 좌표 누락 처리도 검토해야 한다.

배포 없이 PC의 Express/Python/Docker MySQL과 Android 에뮬레이터로 검증할 수 있다.
기본 Android 에뮬레이터의 PC 접근 주소는 10.0.2.2이며 현재 Express 포트는 8080이다.
카카오 지도용 키·앱 등록·SDK 구성은 별도 작업이며 이 문서에서는 구현 완료로 취급하지 않는다.

## 11. 이후 개발 순서

1. 완료된 행신 검색 계층을 가격 비교 HTTP API/앱 필터로 연결하고 매장 좌표·내부 ID 매핑 확보
2. 카카오 지도 화면·마커·메뉴 가격 표시와 추천 결과 연결
3. 에뮬레이터에서 승인된 행신 자료 통합 검증; 추가 실제 데이터는 별도 승인 후 연결
4. 사용자 인증·상태 저장·제안 소유권·요청 제한
5. 후속 대화와 조건 변경 확인 흐름
6. 리뷰 종합 요약 생성기·근거 검증·변경 이벤트 갱신
7. 가입 취향/메뉴 평가/매장 환경 리뷰를 구분해 개인화 순위 구현
8. 운영 배포·보안·관측·비용·응답 시간 평가

추천 원칙은 **현재 요청 > 과거 취향**, **필수 조건 필터 → 순위 계산**이다.
목적 35%·취향 25%·거리 20%·가격 15%·리뷰 5%는 이전 논의의 실험 가설일 뿐,
현재 적용된 점수나 확정된 서비스 정책이 아니다.
