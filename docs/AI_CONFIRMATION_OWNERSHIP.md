# 확인 제안 소유권 — 3단계 격리 구현

현재 백엔드에 인증 미들웨어가 없어 HTTP 연결은 미완료다. `ownedProposals.ts`는 인증 이후 연결할 모듈이며 기존 개발 경로는 아직 이전 토큰을 사용한다. production 차단은 유지한다.

## 구현 및 정책 초안

- 인증 시스템이 검증한 사용자 ID를 issue/verify에 전달한다. body.user_id나 임의 헤더를 인증 근거로 사용하지 않는다.
- JWT와 다른 전용 키를 생성자에 주입한다(최소 32바이트, 실제 배포는 충분한 난수 사용). 무작위 임시 키로 자동 대체하지 않는다. 아직 배포 환경변수와 연결하지 않았다.
- 토큰에 목적·버전·사용자·원문·검증된 제안·발행/만료 시각을 서명한다. 서명은 암호화가 아니므로 원문이 들어 있는 토큰을 로그에 남기지 않는다.
- 타 사용자·변조·잘못된 키·만료·미해결·잘못된 버전/목적/시각은 거절한다. TTL은 공통 정책 600초다.
- 읽기 전용 재검색은 만료 전 반복 허용하는 정책 초안이다. 따라서 제안 검증 자체는 공유 상태 저장소 없이 같은 키로 가능하다. 검색 시 현재 가격을 읽어야 하며 동일 응답 재현/1회 사용은 보장하지 않는다.
- 사용자별 할당량·폐기·멱등 결과 저장이 필요하면 공유 DB/Redis가 별도로 필요하다. 4단계에서 원자적 제한을 구현한다. 단일 메모리 Map은 운영 해법이 아니다.

## 검증과 한계

빌드와 단위 테스트 2개 통과: 독립 객체 간 발행/검증, 새 객체 재생성, 동시 읽기, 타 사용자, 변조, 만료, 다른 키, 잘못된 서명 내용, 미해결 조건 거절.
이는 한 프로세스의 격리 단위 테스트다. 실제 2개 서버·배포 재시작·공유 저장소·로그인 통합 검증은 아니다. 실제 Gemini/DB 호출 없음.

## 연결 전 남은 작업

1. 팀 인증 미들웨어와 검증된 사용자 ID의 서버 전달 위치 확정. 요청의 사용자 ID를 그대로 넘기는 개발 우회 금지.
2. 전용 서명 키 환경 주입/검증, 키 교체·기존 토큰 거절 정책 명시.
3. 준비/확인 서비스에 이 모듈 연결. 기존 토큰은 새 버전으로 오인 수용하지 말고 재준비 안내. 기존 개발 경로에서 모듈만 만들었다고 인증 완료로 표시하지 않음.
4. 최종 조건 전체 표시, 명시적 수정/완화 확인, 누락 필드로 조건을 지우지 않는 계약 적용. verify가 반환하는 원 제안과 수정 조건을 비교하고 unresolved 우회 금지.
5. 직접 추천 경로 공개 범위 결정 및 같은 인증/제한 적용. 2개 서버·동일 키/다른 사용자·재시작·동시 요청 HTTP 검증.

팀 인증 계약 전에는 이 구현을 운영 라우터에 임의로 연결하지 않는다. 독립적인 모의 테스트와 4단계 공유 제한 설계는 진행 가능하다.
