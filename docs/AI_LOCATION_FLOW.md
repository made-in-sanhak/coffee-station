# 위치·거리순 — 6단계 모의 구현

## 요청 계약

prepare에 `location: {latitude: 37, longitude: 127}`을 선택적으로 전달한다. 모의 거리 문장은 `가까운 커피 추천해줘.`다. 위치 없이 준비하면 NEEDS_CLARIFICATION이며 확인은 거절된다. 같은 문장에 위치를 추가해 다시 prepare하면 새 제안으로 확인할 수 있다.

확정 constraints는 기존 필드 외 location, 양수 유한 값 radius_m(미터), sort_by distance를 지원한다. 거리순/반경에는 위치가 필수다. 위도 -90~90, 경도 -180~180의 숫자를 검증한다. 가격순 기본 요청은 기존 형식을 유지한다.

위치 제공 시 서버가 추가했던 거리 연결 안내 마지막 항목만 해소한다. 모델이 반환한 단맛 등 다른 unresolved는 지우지 않는다. 자연어 반경 추출은 아직 지원하지 않으며 구조화된 확정 조건에서 입력한다.

## 데이터와 계산

위치 입력이 있는 모의 조회는 메뉴별로 구분한 synthetic 매장과 (37+(메뉴 번호-1)*0.001, 127) 합성 좌표를 사용한다. 실제 매장 위치와 무관한 테스트 fixture다. 위치 없는 기존 예시에서는 기존 가상 카페 ID를 유지한다.
Haversine 직선거리(미터)를 계산하며 반경 경계 포함 후 정렬·limit를 적용한다. 거리 동률은 가격·offer ID 순이다. 도보 거리/시간으로 표현하지 않는다.

MySQL Repository는 위치/반경/거리순 입력을 명시적으로 거절한다. 실제 좌표 검색 SQL이 연결되기 전에 가격순으로 바꿔 응답하지 않는다. 프런트 타입/화면과 지도 연결은 아직 반영하지 않았다.

## 검증과 남은 작업

빌드 및 관련 테스트 10개 통과: 위치 없음→질문→위치 추가 재준비→확인, 합성 거리순/반경, 다른 미지원 문장 유지, 좌표 범위·타입·반경, 알려진 직선거리, 기존 가격·SQL·HTTP 모의 경로 회귀.
실제 Gemini 거리 추출/지도 API/실제 매장 좌표/에뮬레이터는 미검증이다. 토큰 소유권 새 모듈과 HTTP 인증 연결은 여전히 3단계 미완료다. 기존 개발 토큰의 수정 위치/반경은 확정 조건 입력이며 토큰에 바인딩되지 않는다.

후속: 위치·반경의 화면 계약, 구조화된 미해결 사유 코드(현재 안내 문자열 기반), 실제 좌표/SQL 반경 검색, 위치 개인정보 보관 정책, 반경 정확한 경계·동률·결측 매장 통합 검증을 추가한다. 운영 차단은 유지한다.
