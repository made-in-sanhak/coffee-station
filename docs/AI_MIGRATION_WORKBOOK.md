# AI 기능 전환 작업 지침서 및 단계별 프롬프트

기준일: 2026-11-09. 이 문서는 실행 계획이며 미완료 기능의 구현을 보장하지 않는다.
매 단계 시작 시 실제 코드·ERD·팀 결정의 최신 상태를 먼저 확인한다.

## 1. 목표와 책임

```text
앱 → Express → Gemini 자연어 추출 → 조건 확인 → TypeScript 검색·추천 → 응답
리뷰 변경 → Python Agent → 근거 검증 → 분석 결과 DB 저장
앱 → Express → 저장된 리뷰 분석 조회
```

- 실시간 자연어 추출·검증·추천 계산·HTTP API: Express/TypeScript.
- 리뷰 요약·분석·추천용 구조화 특징 생성: Python Agent 작업.
- Python HTTP 서버는 앱 요청의 필수 의존성에서 제외한다.
- 추천 요청마다 리뷰 분석을 실행하지 않는다. 변경 시 갱신한 결과를 재사용한다.
- 현재 요청 > 가입 취향/과거 행동. 필수 조건 필터 → 후보 점수 → 정렬 순서를 지킨다.

| 영역 | 현재 상태 | 남은 문제 |

### 코드 대조 검토 (2026-11-09)

방향과 책임 분리는 적절하지만 아래는 아직 구현된 보호 장치가 아니다.

- `backend/src/recommendations/proposals.ts`: 서명은 추출 제안과 만료를 보호한다. `/confirm`의 수정 조건은 별도 입력이며 원래 제안과 비교하지 않는다. 사용자 수정 자체는 허용하되 수정 가능 필드와 재확인 규칙을 계약으로 정해야 한다.
- `backend/src/routes/recommendations.ts`: 직접 추천 `/`는 제안 토큰 없이 호출할 수 있다. 구조화 조건을 직접 입력하는 정식 경로인지 개발 전용인지 결정해야 한다. 운영화할 때 인증·제한의 우회 경로가 되어서는 안 된다.
- `backend/src/routes/reviewSummaries.ts`: 2단계에서 production 503을 추가했다. 파일 내용의 전체 응답 스키마 검증은 아직 부족하다.
- `backend/tests/recommendations.cjs`: 2단계에서 임시 자료 생성·정리를 구현했다. 다만 모듈 로드 시 상속 환경과 전역 설정 변경에 의존하며 생산 환경 시작 검증까지 증명하지는 않는다.

## 3. 모든 작업에 적용할 규칙

1. 한 번에 한 단계만 구현한다. 변경 파일·목적·검증 명령·결과·남은 제한을 보고한다.
2. Git 명령, 커밋·푸시·PR·머지는 사용자가 직접 한다. 별도 요청 없이 실행하지 않는다.
3. 기본 데이터는 모의 자료다. 승인된 행신 자료 외 다른 실제 데이터는 추가 지시 없이 사용하지 않는다.
4. 실제 Gemini 호출은 별도로 요청받은 평가에서만 수행한다. 테스트 기본값은 외부 API 호출 0회다.
5. 키·토큰·개인정보를 코드/노트북 출력/로그에 저장하지 않는다. 환경 예시는 빈 값/예시만 사용한다.
6. 프런트는 담당자와 API·진입점 합의 전 임의 재구성하지 않는다. 로그인·지도·탭바를 보존한다.
7. 확정 예산·거리·취향을 자동 완화하거나 지원하지 않는 조건을 조용히 버리지 않는다.
8. 자료 부족을 0원·임의 좌표·가짜 검증일로 채우지 않는다. 출처와 미확인 상태를 유지한다.
9. DB DDL/쓰기/삭제/운영 설정 변경은 적용 범위를 먼저 명시한다. 기존 볼륨 삭제로 문제를 해결하지 않는다.
10. 작업 중 팀 변경이나 계약 충돌이 발견되면 충돌 지점과 대안을 제시한다. 근거 없이 기능을 확장하지 않는다.

## 4. 단계별 실행 계획

기본 순서는 1→12다. 단, 외부 합의나 공유 저장소가 준비되지 않았다는 이유로 독립적인 모의 개발까지 멈추지 않는다.

| 작업 묶음 | 진입·완료 기준 |
|---|---|
| 1~2 계약·기반 | 현재/목표 계약을 구분하고, 키·DB·사전 생성 파일 없이 모의 테스트가 실행됨 |
| 3~4 운영 보호 | 인증 계약 확정 후 구현. 두 서버의 공유 상태·할당량은 실제 격리 저장소 통합 테스트까지 통과해야 운영 완료로 표시 |
| 5~6 검색·위치 | 1~2 후 모의 구현 가능. 실제 연동 완료는 스키마·좌표·승인된 DB 검증이 있어야 표시 |
| 7~9 분석·순위 | 1~2 후 7~8의 모의 작업 가능. 9는 5의 후보 계약과 7~8의 검증된 특징 계약에 의존 |

| 12 배포 | 앞 단계의 해당 운영 필수 검증과 팀 결정 완료. 로컬 시연 성공만으로 차단 해제 금지 |

### 2단계 — 설정·모듈·모의 실행 경로 정리

진행 기록(2026-11-09): 계약/추출/서명/모의 Repository 분리, 시작 시 설정 검증, 임시 파일 기반 독립 테스트, 모의 리뷰 운영 503 적용. 빌드 및 Node 테스트 2개 통과. 응답·토큰 형식 유지, 잘못된 설정은 요청 시점 대신 시작 시점에 실패하도록 변경. SQL 선택/TLS는 실제 경로가 없는 상태이므로 5단계에 남긴다. 3단계의 인증 사용자 식별 계약·공유 저장소는 아직 미확정이다.

- 선행: 1단계 계약 초안.
- 변경: 라우터의 입력 처리, 추출 서비스, 추천 서비스, Repository, 설정을 책임별로 분리.
- 설정: 모의/실제 추출, DB 선택, TLS, 제한값을 단일 설정 모듈에서 검증. 요청 처리 중 .env 재독해 금지.

- 운영 분리: 모의 리뷰 파일 경로도 기본 운영 등록에서 제외한다. 추천·리뷰 각 경로의 운영 차단을 별도로 테스트한다.
- 테스트 독립성: 분석 파일을 임시 경로에서 테스트가 생성·정리하게 하고, 외부 요청을 차단한 상태에서 실행한다. 개발자의 `.env`와 기존 artifact에 의존하지 않는다.
- 지킬 것: 이전 HMAC/응답 형식을 조용히 바꾸지 말고 버전/호환 정책 기록.

```text

동작을 불필요하게 바꾸지 말고 설정 오류와 모의 무외부호출을 검증하라.
```

### 3단계 — 사용자 인증·제안 소유권·공유 상태

진행 기록: [소유권 계약 및 격리 구현](AI_CONFIRMATION_OWNERSHIP.md) 작성. ownedProposals.ts에 전용 키/사용자/목적/버전/시각 검증 구현, 빌드 및 단위 테스트 2개 통과. 인증 미들웨어가 없어 HTTP 통합은 미완료이며 기존 개발 경로는 이전 토큰을 사용한다. 같은 키를 쓰는 독립 객체/재생성/동시 읽기를 검증했으나 실제 다중 서버·공유 저장소 검증은 아니다. 반복 가능한 읽기 전용 재검색 정책 초안을 적용했다. 운영 차단은 유지하며 다음은 인증 계약 확인 후 연결 또는 독립 공유 제한 설계다.

- 선행: 사용자 식별 계약. 인증 체계가 없으면 먼저 통합 방안을 합의.
- 구현: 서버가 검증한 사용자 ID를 사용. body의 user_id를 신뢰하지 않음.
- 변경: 임시 토큰/공유 상태 방식을 결정. 서명 키는 인증 JWT와 목적 분리 및 환경 주입.
- 다중 서버: 공통 키/TTL/스키마 버전. 단일 메모리 Map에 의존하지 않음.
- 재사용: 원자적 1회 소비 또는 멱등 요청키로 같은 결과 반환 중 정책 선택. 실패 후 재시도 정책 명시.
- 결정 기준: 읽기 전용 확인에 1회 소비를 무조건 강제하지 않는다. 중복 추천 허용 여부·가격 갱신·동일 결과 재사용을 합의하고, 멱등 키를 쓰면 사용자와 확정 조건 해시에 묶는다. 다른 조건으로 같은 키를 재사용하면 거절한다.
- 검증: A가 준비→B가 확인, 다른 사용자 거절, 변조·만료·중복·서버 재시작·동시 확인.
- 지킬 것: 현재 운영 차단을 먼저 제거하지 않는다. hmac 비교는 timingSafeEqual 등 사용.

```text
3단계를 수행하라. 현재 인증 체계를 먼저 확인하고 제안을 검증된 사용자에 바인딩하라.
공유 저장소가 없으면 도입 대안과 마이그레이션을 제시한 뒤 격리 테스트용 구현을 구성하라.
다중 인스턴스·만료·변조·타 사용자·동시 소비를 테스트하고 운영 차단은 유지하라.
```

### 4단계 — 사용자별 공유 호출 제한·시간 예산

이번 평가에서 TypeScript 빌드를 다시 실행해 성공했다. 빌드된 contracts 함수에 아래 입력을 직접 전달해 재현했다(네트워크·DB·LLM 호출 없음).

1. `conditions({category:["COFFEE"]})`가 배열을 그대로 반환한다. `String(category)`로 허용값을 비교한 뒤 타입 단언으로 반환하기 때문이다. HTTP JSON으로도 입력 가능한 형태이며 실제 분류 비교에서는 일치하지 않아 잘못된 빈 결과를 만들 수 있다.

### 2단계 보완 A — 입력 및 제공자 응답 검증 (우선)

진행 기록: 구현 완료. category 배열/객체/숫자/boolean 거절, 모델 값 오류 502 변환, mock/Gemini 공통 검증 및 입력 불변성 적용. fetch 주입으로 외부 호출 없이 제공자 응답 테스트. TypeScript 빌드와 `node --test backend/tests/extraction.cjs` 3개 테스트 통과(타입/경계, 입력 불변성, 모의 제공자 성공·JSON 오류·근거 오류·후보 없음·429·503·시간 초과). 다음 작업은 보완 B다. 아래 평가의 재현 결함 2건은 이 기록으로 해결되었으며 나머지 보완은 유지한다.

- 대상: `recommendations/contracts.ts`, `recommendations/extraction.ts`, 관련 테스트.
- category는 null 또는 허용된 **문자열**만 받는다. 배열·객체·숫자·boolean을 변환하여 수용하지 않는다.
- 사용자 conditions 오류는 422, 모델 출력 스키마/값/근거 오류는 502로 구분한다. 제공자의 원문/비밀값을 오류 메시지에 넣지 않는다.
- mock과 Gemini 출력에 같은 검증 규칙을 적용한다. 검증 중 입력의 unresolved 배열을 변경하지 않고 검증된 새 결과를 반환한다.

- 제공자 테스트: 실제 fetch 대신 주입한 응답으로 정상 JSON, 잘못된 JSON/근거/필드, 후보 없음, 429/503/시간 초과를 재현. 실제 Gemini는 호출하지 않는다.

### 2단계 보완 B — 리뷰 산출물과 테스트 신뢰도

진행 기록: 구현 완료. reviewArtifact 검증 모듈에서 객체/상태/매장/리뷰 수/출처 ID/시각/의견 타입·허용값을 검사하며 손상 자료는 503으로 처리한다. 원문 근거 검증은 Python 작업의 책임으로 유지한다. 테스트는 정상 표시 계약 fixture와 null/누락/타 매장/잘못된 의견을 검사하고 추천 ID·가격·순서·RESULT/QUESTION·모의 표시를 확인한다. LATTE+limit 별도 검증도 추가했다. 임시 서버 origin 제한, PORT/DB_PORT 고정, 시작 실패 시 정리 경로를 보완했다. production은 별도 프로세스에서 실제 설정으로 시작해 4개 경로 503을 검증했다. 빌드 성공, 기존·추출·운영 테스트 6개와 별도 catalog 테스트 1개 통과(총 7개). 외부 API/실제 DB 호출 없음. 운영 검증은 로컬 프로세스이며 Docker/ALB 검증을 대체하지 않는다. 다음은 보완 C다.

- 대상: `routes/reviewSummaries.ts`, `tests/recommendations.cjs`, 검증에 필요한 작은 모듈.
- 현재 리뷰 조회는 data_mode와 cafe_id만 확인한다. 테스트도 review_count만 있는 불완전한 JSON을 200으로 통과시킨다. 프런트는 opinions 배열을 요구하므로 현재 테스트로 화면 호환을 보장할 수 없다.
- JSON `null`은 파싱에 성공한 뒤 data.data_mode 접근에서 예외가 나므로 현재 500이 될 수 있다. 객체 여부와 필수 필드를 검증하고 손상/누락 산출물은 일관된 503으로 처리한다.
- 실제 내보내기 형식에 맞는 fixture를 사용해 status·review_count·generated_at·opinions 등의 타입과 허용값을 확인한다. 형식 검증과 원문 근거 검증의 책임은 구분한다.
- 추천 검증은 개수 외에 ID·가격·순서·RESULT/QUESTION·모의 표시를 단언한다. 별도 테스트로 limit와 분류를 검증한다.
- 테스트는 설정/Repository/제공자 의존성을 주입하거나 격리 프로세스로 실행한다. 현재 env.nodeEnv를 실행 중 변경하는 검증은 운영 설정으로 실제 시작하는 검증을 대체하지 않는다.
- PORT/DB_PORT 등 상속 환경도 고정한다. 임시 폴더/서버 정리는 서버 시작 실패에도 실행되게 한다. fetch 제한은 해당 임시 서버 origin으로 한정한다. 현재 fetch/일부 pool 메서드 치환은 모든 네트워크를 차단하는 샌드박스가 아니다.
- 완료 기준: null/필드 누락/잘못된 타입/잘못된 매장/정상 리뷰, 개별 독립 실행, 운영 설정 시작 시 모든 모의 경로 503, 키·DB·기존 artifact 없이 재현.

```text

```

### 2단계 보완 C — 설정·문서의 완료 범위 정리

진행 기록: 구현 완료. aiPolicy.ts에 TTL/제공자 시간/로컬 제한을 모으고 기존 기본값 유지. 응답 TTL과 서명 만료 계산 일치, 잘못된 설정의 격리 시작 실패 검증 추가. 빌드 및 전체 관련 테스트 9개 통과. 문서에 production 지정 전제와 시작 오류를 명시하고 모의 노트북에서 자동 테스트 전 Python 내보내기 선행을 제거했다. 노트북 JSON/코드 구문은 검사했으며 전체 셀 실행은 하지 않았다. 다음은 3단계 인증·소유권·공유 상태 계약이다. Docker/실제 DB/실제 LLM 검증은 미실행이다.

- 현재 제한 10회/분, 제안 TTL 600초, 제공자 시간 30초는 여러 파일에 상수로 남아 있다. 검증 가능한 단일 설정/상수 정의로 모으고 TTL 응답과 실제 만료 계산이 같도록 한다. 모든 상수를 환경변수로 늘릴 필요는 없다.

- API 계약서의 시작 설정 오류와 요청 오류를 구분하고 초기 검토 문구를 현재 상태로 갱신한다. 노트북의 Python 내보내기는 수동 리뷰 시연용이며 자동 테스트의 필수 선행이 아님을 표시한다.
- 완료 기준: 잘못된 설정의 시작 실패 테스트, 기존 기본값 호환, 문서/노트북 안내와 실제 실행 순서 일치.

