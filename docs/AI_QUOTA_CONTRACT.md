# 사용자별 AI 호출 제한 — 4단계 격리 구현

`quota.ts`의 QuotaStore는 사용자별 분당/일일 시도 횟수와 동시 실행 lease를 원자적으로 예약하는 계약이다. createQuota는 서버가 검증한 사용자 ID만 받으며 저장소 장애는 503으로 닫는다. 제한 초과 오류에는 Retry-After로 전달할 초 수가 있다. HTTP 연결은 아직 하지 않았다.

## 정책 초안

- 제공자 호출 직전에 예약한다. 승인된 예약은 성공/실패와 무관하게 1회 차감하며 환불하지 않는다. 재시도마다 새 예약이 필요하다. 거절된 예약은 차감하지 않는다.
- 분당은 최근 60초, 일일은 UTC 자정 기준이다. 숫자는 호출 정책 합의 후 주입한다. 테스트 숫자는 운영 권장량이 아니다.
- 호출 종료 시 반환된 release를 finally에서 실행한다. release는 동일 lease를 반복 해제해도 안전하다. 프로세스 중단 시 lease 만료로 회수한다.
- lease 시간은 실제 호출 취소·종료 예산보다 길어야 한다. 작업이 lease보다 오래 실행되면 동시 제한이 깨질 수 있으므로 전체 기한/취소 통합 전 운영 사용 금지다.
- 직접 검색/모의 추출은 LLM 할당량과 별도 정책이며 이를 실제 제공자 시도로 잘못 차감하지 않는다.

## 저장소 선택

기존 MySQL을 이용한다면 사용자별 상태 행을 트랜잭션으로 잠그고 카운터·lease를 함께 갱신하는 구현을 우선 검토한다. Redis는 원자적 스크립트로 구현할 수 있으나 별도 운영 의존성이 생긴다. 어느 쪽이든 서버가 아닌 공유 저장소 시간을 기준으로 검사하고 장애 시 우회하지 않는다. DB/Redis 선택·스키마는 팀 합의 전이다.

MockQuotaStore는 한 프로세스에서 원자 동작을 흉내 내는 테스트 전용 Map이다. 실제 공유 저장소나 운영 제한으로 사용하지 않는다. 테스트 2개에서 두 서비스 객체의 합산·동시 경쟁·분/일 경계·사용자 분리·중복 해제·lease 회수·저장소 장애를 검증했다. 실제 다중 프로세스/DB/Redis 검증은 미완료다.

## 남은 연결

1. 인증된 사용자 전달 계약 및 실제 공유 저장소 구현.
2. 추출에 예약/해제 연결, 사용자 취소·전체 기한·제공자 AbortSignal 연결, 유한 재시도와 재예약 검증.
3. HTTP 429에 Retry-After 반영, 요청 ID/지연/시도 횟수만 기록(원문·토큰 제외).
4. lease보다 오래 걸리는 호출과 저장소 지연/장애, UTC 자정 근처 분당 제한, 실제 두 서버 합산을 통합 테스트.

기존 라우터의 로컬 IP 제한과 production 503은 유지한다. 4단계 전체 완료로 표시하지 않는다.
