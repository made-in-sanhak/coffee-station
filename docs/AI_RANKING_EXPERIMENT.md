# 리뷰 특징과 추천 순위 — 9단계 모의 실험

`recommendations/ranking.ts`에 독립 순위 모듈을 구현했다. HTTP 추천 경로는 기존 가격/거리 정렬을 유지하며 이 모듈을 자동 호출하지 않는다.

## 계산 계약

- 후보의 가격·분류·반경 등 필수 조건을 먼저 검사한다. 높은 점수로 필수 조건 위반 후보를 복구하지 않는다.
- 매장별 현재 revision과 분석 revision이 같은 특징만 사용한다. 동일 매장 특징이 여러 개면 모호하므로 사용하지 않는다.
- 목적 topic(noise/seating)의 reviewId별 의견을 집계한다. 중복 인용은 중복 투표하지 않고 같은 리뷰의 상반 분류도 투표에서 제외한다.
- 리뷰 신호 = (긍정 수 - 부정 수) / (긍정 수 + 부정 수 + smoothing). 표본이 적으면 0 쪽으로 보정한다. 상반 의견·긍정/부정 수·특징 유무를 결과에 보존한다.
- 총점 = 리뷰 신호×review 가중치 + 메뉴 분류 취향 일치×preference 가중치. 가중치·보정값은 호출자가 명시하는 실험값이며 운영 기본값은 정하지 않았다. 취향이 없으면 일치 보너스는 0이다.
- 실험 order는 price/distance/relevance다. price/distance에서는 점수로 순서를 뒤집지 않는다. relevance는 오프라인 비교용이며 현재 자연어/API 계약에는 추가하지 않았다. 동률은 가격·offer ID로 고정한다.

## 검증 및 제한

빌드와 테스트 3개 통과: 필수 필터 우선, 오래된/없는 특징, 중복·상반 의견, 명시적 가격/거리순 보존. 실제 LLM/DB 호출은 없다.

기존 Python 분석의 ID/분류를 이 입력으로 변환하고 현재 revision을 신뢰할 수 있는 저장소에서 읽는 어댑터는 미구현이다. reviewId와 분류는 검증된 분석에서만 공급해야 하며 클라이언트 입력을 특징으로 신뢰하지 않는다. 리뷰 의견은 객관적 매장 사실이나 메뉴 평가가 아니다.

추천에 연결하려면 Repository가 먼저 limit한 일부 가격 후보만 점수화하지 않도록 후보 검색/페이지 계약을 정해야 한다. 충분한 후보의 필터→점수→최종 limit 순서를 보장하고 매장 다양성/신규 매장 처리도 평가한다. 현재 단순 표본 실험으로 추천 품질을 주장하지 않는다.

팀 합의 후 목적·취향의 필수/선호 구분, 조용함 외 seating 긍정의 의미, 가중치·신선도·최소 표본·다양성 정책을 정한다. 요청에서 정한 정렬을 relevance로 자동 전환하지 않는다. 프런트 통합은 담당자 계약 후 진행한다.
