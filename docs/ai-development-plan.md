# AI 개발 계획과 작업 규칙

중간발표 우선순위(2026-11-10): [AI 추천 MVP 계획·프롬프트](midterm-ai-mvp-plan.md)를 먼저 따른다. 칩/자연어 조건으로 Express가 DB 후보를 검색·정렬하는 최소 흐름을 우선하며 Python 리뷰 Agent는 이번 서비스 실행에 넣지 않는다. 장기 과제는 아래에 유지한다. 첨부 기준의 mock APK·AWS health 분리 시연과 실제 추천 연결 목표를 혼동하지 않는다.

기준: 2026-11-10. [실시간 추천](ai-recommendation.md)과 [리뷰 분석](ai-review-analysis.md)의 현재 구현을 기준으로 한다. 이 문서는 미완료 기능의 구현을 주장하지 않는다.

## 책임과 진행 순서

### 파일 구조 정리 진행 (2026-11-10)

1단계 완료: Express 추천 코드를 `backend/src/modules/recommendations/`에 모으고 리뷰 조회·검증을 `modules/reviewSummaries/`로 분리했다. 소스 12개 이동, app 등록·테스트 import·현재 안내 문서 경로를 수정했다. 비어 있는 이전 recommendations/services 소스 폴더는 제거했다. HTTP 계약·설정값·운영 차단은 변경하지 않았다. TypeScript 빌드와 백엔드 테스트 20개 통과, 소스·테스트의 이전 import 잔여 없음. 실제 DB/외부 API/Git 작업 없음.

2단계 완료: 작업 시작 시 소스·현재 문서·노트북 경로가 이미 ai-jobs로 변경돼 있어 해당 변경을 유지하고 검증했다. 새 위치의 Python executable/prefix를 확인했으며 테스트 16개와 export 실행이 통과했다. 최초 샌드박스 TEMP의 SQLite 접근 실패 후 로컬 재실행으로 확인했다. ai-server에는 로컬 .venv만 남아 있으며 사용자 환경은 삭제하지 않았다. 실제 DB/API/Git 작업 없음.

3단계 완료: 현재 계약·제한·프런트 통합 기준을 핵심 문서에 이관하고 단계별/마이그레이션/PR 답변 문서를 삭제했다. 5단계 전체 회귀까지 완료했다. 프런트 화면 통합은 담당자 합의 전까지 제외한다.

`앱 → Express → Gemini 조건 제안 → 사용자 확인 → TypeScript 검색·추천`과 `리뷰 변경 → Python 작업 → 근거 검증 → 분석 저장 → Express 조회`를 목표로 한다. 현재는 모의 추천과 별도 모의 리뷰 파일 조회다.

1. 프런트 담당자와 #9 화면 진입점, prepare/confirm/결과, 위치와 오류 계약을 합의한다. 로그인·지도·탭은 합의 없이 재구성하지 않는다.
2. 인증된 사용자 ID를 확인 제안에 연결하고 수정·완화 규칙을 정한다. 직접 추천 경로에도 같은 인증·제한 정책을 적용한다.
3. 사용자별 호출 제한을 공유 저장소와 통합한다. 제공자 호출 예산, 취소, 재시도, lease 회수와 두 서버 동시 요청을 검증한다. 현재 `quota.ts`는 격리 모의 구현이다.
4. 검증된 매장·가격·좌표 데이터의 출처와 판매 상태를 확보한 뒤 TypeScript 조회 경로에 연결한다. 행신 staging 가격은 현재 판매 추천으로 간주하지 않는다.
5. Python 리뷰 분석을 실제 저장소·변경 이벤트·실패 재처리에 연결하고, Express가 현재 revision의 결과만 조회하도록 한다. 리뷰 특징 순위는 충분한 후보의 필터·점수·최종 limit 순서와 품질 평가 뒤 연결한다.
6. 승인된 평가에서 실제 Gemini 추출 품질과 오류·비용을 확인하고, 운영 환경에서 인증·공유 제한·DB·배포를 통합 검증한다. 운영 차단 해제는 이 검증 뒤 결정한다.

## 매 작업 원칙

현재 코드·계약·ERD·팀 결정을 다시 확인한다. 모의 데이터와 모의 LLM을 기본으로 하며 실제 Gemini, 다른 실제 자료, DB 쓰기·삭제는 명시된 범위에서만 다룬다. 키·토큰·개인정보를 코드·노트북 출력·로그에 남기지 않는다. 사용자 필수 조건을 자동 완화하거나 출처·검증일·좌표 누락을 가짜 값으로 채우지 않는다. 구현·모의 검증·실제 통합 검증을 다른 상태로 보고한다. 한 단계씩 변경 파일, 실행 명령, 결과, 남은 제한, 다음 진입 조건을 기록한다. Git 작업은 사용자가 직접 한다.

배포 구성과 운영 전 검증은 [배포 안내](deployment.md)를 따른다. 이전 실습 구현과 작업 기록은 별도 archive로 보존하지 않는다. 행신 원본·적재 재현 자료와 현재 리뷰 작업·export·노트북은 유지한다. 프런트 실험 화면은 담당자 합의 후 정리한다.

## 프런트 변경 수용 원칙

프런트 작업이 추가돼도 전체 리팩터링을 반복하지 않는다. 같은 기능의 화면/API 계약이 겹치는 부분만 통합한다. 기존 API 경로·응답 호환성을 유지하고 변경 시 양쪽 타입·fixture·테스트를 함께 갱신한다. 이전 백엔드 경로를 수정한 브랜치는 현재 modules 구조에 맞춰 충돌을 해결한다. 로그인·지도·탭 변경은 담당자 합의 후 진행한다.

## 프런트 브랜치 통합 시 확인 목록

담당자가 알려준 최신 브랜치를 Git으로 받아 차이를 검토한 뒤 현재 작업과 합친다. 폴더를 다운로드해 덮어쓰지 않는다. 실제 fetch/merge/commit/push는 사용자가 수행한다. 통합 전에 작업 트리·브랜치·변경 파일을 확인하고 예상하지 못한 변경은 보존한다.

- 화면: #9와 독립 추천/리뷰 화면의 역할을 합의해 하나의 진입점으로 정리한다. screens/recommend/, api/endpoints/, api/queries/ 규칙을 팀과 확인한다. 로그인·지도·탭을 임의 교체하지 않는다.
- API: prepare/confirm/결과/오류의 요청·응답 타입과 fixture를 통일한다. 프런트 mock 전용 거절 로직, 서버 null 조건과 로컬 예시 조건 차이, 로컬 limit 미적용을 확인한다. 사용자 위치/지도 중심·반경과 미지원 조건 처리도 합의한다.
- 식별자: 추천 문자열 cafe.id/menu_id/offer.id, 지도 숫자 Store.id, Kakao 장소 ID를 구분한다. COFFEE/LATTE/TEA/ETC를 AMERICANO/LATTE/DECAF와 자동 대응하지 않는다. 특히 COFFEE는 아메리카노와 같지 않다.
- 지도: recommendationMap 어댑터는 명시적·유일한 ID 매핑과 기존 Store 좌표가 있어야 READY다. 모의 추천·매핑/매장 누락·중복·좌표 오류는 연결 불가이며 ID/좌표를 만들지 않는다. 지도 카드 가격과 추천 옵션 가격이 같다는 보장도 없으므로 메뉴/옵션 계약을 함께 확인한다.
- UX: 원문/위치/모드 변경 시 제안 무효화, 최종 수정/완화 확인, 로딩/중복 버튼/취소/빈 결과/429·Retry-After/만료·재준비. 현재 apiFetch가 HTTP 상태를 보존하지 않는 문제도 해결 대상이다.
- 검증: 프런트 타입·렌더/API 테스트와 백엔드 계약 테스트 후 에뮬레이터에서 10.0.2.2:8080 연결, 위치 권한 거부·화면 복귀·조회 범위 밖 매장·마커 선택을 확인한다. 실제 지도/DB/LLM 검증은 별도 승인 범위에서만 한다.

## 평가와 다음 작업 기준

실제 Gemini 평가 전 대표 입력/정답/근거, 표본 수·호출 상한·합격 기준을 고정한다. 이하/미만·가격순·복수/충돌·위치/미지원·프롬프트 주입·상반 리뷰를 포함한다. 형식/의미 정확도·미지원 보존·근거 유효율·조건 위반·호출 수/지연/토큰/실패율을 분리하고 호출 실패를 분모에서 빼지 않는다. 일시 오류 연속 시 중단하며 실제 호출은 별도 승인 후 진행한다.

각 단계는 변경 목록·목적→구현→해당 테스트→미완료/다음 조건 순으로 진행한다. 실제 DB/DDL/쓰기/배포는 범위를 먼저 명시하며 기존 볼륨을 삭제하지 않는다. 구현·모의 검증·실제 통합을 구분하고 운영 차단 해제는 인증·소유권·공유 제한·DB·배포 검증 이후에만 결정한다.

## 모의 화면과 리팩터링 검증

독립 RecommendationScreen/ReviewSummaryScreen은 현재 RootNavigator의 기본 화면이 아니다. 로그인/지도/탭 연결은 프런트 담당자 합의 후 진행한다. 모의 화면 local은 네트워크 없이 동작하고 server는 Express API를 사용한다. Python HTTP·내부 토큰은 불필요하다. 수동 리뷰 조회만 Python export 파일 생성이 선행된다. 서명 토큰의 서버 확인은 1회 소비가 아니지만 현재 화면은 확인 후 제안을 비워 새로 준비하게 한다. 실제 기기/시각 검증은 미완료다. Android는 client.ts의 10.0.2.2:8080을 사용하며 PC Express 연결 상태를 확인한다. 실제 기기/iOS 주소는 별도 환경 설정이 필요하다.

4단계 완료(2026-11-10): ai-jobs/.venv를 명시한 임시 Jupyter 커널로 모의 노트북 코드 셀 4개를 순서대로 실행했다. SQLite 요약/수정/삭제/캐시, Express 빌드 및 HTTP 모의 테스트 2개, 리뷰 Agent 실행이 통과했다. 실제 자료 노트북은 실행하지 않고 구문·RUN_HAENGSIN_TEST=False를 확인했다. 두 노트북 형식·셀 ID·출력/실행 번호 초기화를 검증했다. 삭제 모듈·이전 import·문서 링크 참조를 확인했고, 잘못된 Python 서버/기본 화면 안내를 담은 프런트 모의 화면 문서 2개는 이 절로 통합했다. 빈 ai-jobs/fixtures와 sql은 제거했다. 실제 DB/LLM/지도/Git 작업 없음.

## 최종 회귀 결과 (2026-11-10)

파일 구조 정리 1~5단계를 완료했다. 백엔드 기능 모듈 통합, Python ai-jobs 경로 확인, 문서 5개 통합, 모의 노트북 전체 실행과 출력 초기화, 전체 회귀를 수행했다.

| 검증 | 실제 결과 |
|---|---|
| backend npm run build + 전체 tests/*.cjs | 빌드 성공, 20개 통과 |
| ai-jobs unittest discover -s tests -p test_*.py | 16개 통과 |
| frontend tsc --noEmit + Jest --runInBand | 타입 검사 성공, 5 suite/9개 통과 |
| 로컬/운영 docker compose config --quiet | 모두 성공, 구성 검증만 수행 |
| 현재 문서 상대 링크 | 28개 검사, 누락 없음 |
| 노트북 | 모의 4셀 전체 실행 완료, 실제 데이터 노트북 미실행·DB False, 저장 출력/실행 번호 없음 |
| 코드·설정의 이전 Python 추천/HTTP·이전 TS import | 검색된 잔여 참조 없음 |

테스트는 모의 자료·주입 실행기·임시 SQLite·localhost만 사용했다. 실제 Gemini/지도/DB, Docker 이미지 빌드·컨테이너 시작, 실제 다중 서버/에뮬레이터/운영 배포는 검증하지 않았다. Git 변경·원격 게시도 수행하지 않았다. 로컬 이전 ai-server/.venv는 사용자 환경으로 남겼으며 소스 보존용 폴더가 아니다.

이후 작업은 구조 재정리가 아니라 위 기능 개발 순서(프런트 계약·인증/공유 제한·실제 DB·리뷰 분석 저장/조회·품질 평가)에 따른다. 현재 생산 환경 503 차단은 그대로다.
