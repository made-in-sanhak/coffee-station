# 중간발표 AI 추천 MVP — 실행 계획과 단계별 프롬프트

기준일: 2026-11-10. 발표 기준일: 첨부 MVP 문서의 2026-11-13.
상태: 계획만 작성. 아래 기능 추가·DB 연결·실제 Gemini 호출·배포는 이번 작업에서 실행하지 않았다.

## 1. 이번 개발의 우선순위

사용자는 촉박한 일정에 맞춰 선택 조건/자연어 기반 DB 추천을 우선하고, Python 리뷰 Agent는 지속 개발하되 실제 서비스에는 아직 넣지 않기로 했다. 이 계획은 해당 AI 추천 작업에 한해 [장기 개발 계획](ai-development-plan.md)의 우선순위를 조정한다. 영수증/OCR/쿠폰/커뮤니티/결제 전체를 이번 AI 작업에서 구현하지 않는다.

첨부 「MVP 정리(중간발표용)」는 앱을 mock APK로 시연하고 AWS는 health/이중화를 별도로 시연하도록 정리했다. 이는 사용자 자료의 기준이며 실제 배포 상태를 이번에 검증한 것은 아니다. 새 Gemini/DB 기능은 **로컬 제한 시연 → 앱 연결 → 배포 가능 여부 판단** 순서로 준비하고, 기존 mock APK 시연을 새 기능의 성공 조건으로 묶지 않는다. PR #16 화면 통합 상태 역시 첨부 설명이며 현재 원격 코드를 조회·검증한 상태가 아니다.

### 최소 성공 흐름

```text
선택 조건(칩) → Express 입력 검증 ───────────┐
자연어 → Express → Gemini 조건 추출 → 사용자 확인 ─┤
                                               ↓
                              서버의 필수 조건 필터·DB 검색·정렬
                                               ↓
                        DB의 메뉴/매장/가격 + 근거 기반 이유·태그
```

- Gemini에는 DB 계정이나 임의 SQL 실행 권한을 주지 않는다. 모델이 가격·매장·옵션을 만들어 추천하지 않는다.
- 선택 칩은 이미 구조화된 입력이므로 LLM 호출 없이 검색한다. 자연어만 Gemini로 해석한다.
- 추천 순위와 가격은 서버/DB가 결정한다. 우선 구현할 이유는 조건 충족 사실의 템플릿이다.
- Gemini 이유 문장은 선택 확장이다. 필요 시 서버가 확정한 후보/근거만 전달하고 출력 검증 후 사용한다. 이유 생성 실패로 검색 결과를 버리지 않는다.
- 이번 흐름에는 Python 작업, 리뷰 요약/키워드 Agent, ReAct/다중 도구 loop를 연결하지 않는다. 기존 Python 코드는 삭제하지 않고 독립 테스트 상태로 유지한다.

## 2. 현재 출발점과 필요한 차이

| 항목 | 현재 로컬 구현 | 이번에 필요한 작업 |
|---|---|---|
| Express API | modules/recommendations의 prepare/confirm/직접 추천 | 기존 경로 재사용, 칩·자연어 조건 계약 통일 |
| 추출 | Gemini REST 및 원문 근거 검증, mock 예시 | 발표 대표 문장 범위·응답 오류·한도 검증 |
| 검색 | 기본 모의 메뉴 6개 | 실제 연결 풀을 주입한 명시적 demo DB 모드 |
| MySQL Repository | 주입 SQL/선별 매장/가격·분류 필터 | 최신 스키마 대조·설정/연결·읽기 전용·오류 처리 |
| 메뉴 | COFFEE/LATTE 등의 category | 아메리카노/카페라떼의 정확한 메뉴 식별자·옵션 조건 |
| 거리 | 합성 좌표, SQL 거리 요청 거절 | 좌표가 준비된 경우만 실제 반경/거리순 구현 |
| 목적·취향·태그 | 실제 추천 DB 근거 부족 | 지원 필드·데이터 없는 조건을 명시, 임의 추정 금지 |
| 소유권/제한 | 격리 모듈, HTTP 인증/공유 저장소 미연결 | 공개 배포 선행 조건 확인, 로컬 개발과 운영 구분 |
| 화면 | 로컬 독립 모의 화면/기존 지도 | 담당자가 제공하는 최신 프런트와 DTO·진입점 합의 |
| 리뷰 Agent | ai-jobs의 모의 분석/저장 계약 | 이번 추천 실행 경로에서는 제외 |

## 3. 범위와 데이터 원칙

### 우선 지원할 조건

1. 정확한 메뉴: 아메리카노·카페라떼. 기본 아이스 아메리카노라는 MVP 의도는 화면에서 기본 선택으로 표시하고, 자연어에 없는 메뉴/온도를 추출된 사실처럼 표시하지 않는다.
2. 최대 가격: 원 단위, 이하 포함/미만 차감. 온도·사이즈는 DB가 구분하는 경우에만 정확히 필터한다.
3. 가격순. 거리순·반경은 실제 좌표가 준비된 경우에만 활성화한다.
4. 추천 카드: 매장/메뉴/가격 옵션 ID·가격·출처·확인일·검증 상태, 서버가 설명할 수 있는 이유/태그.

평점 정렬은 신뢰할 수 있는 평점·표본이 있고 정의가 합의된 경우에만 추가한다. 공부/조용함/단맛/디카페인/취향 등은 근거 필드가 없는 상태에서 충족했다고 말하지 않는다. 미지원 조건은 표시·확인하거나 지원하지 않는다고 반환한다. 사용자가 해제하기 전 임의로 제외하지 않는다.

### DB 선택

- 기본 개발은 fixture/mock이다. 별도 소량 demo DB(메뉴 10개 이하)를 준비하면 원본과 격리된 seed·cleanup·DB명/모드 설정을 둔다. cleanup은 특정 demo 대상만 삭제하며 사용자의 직접 실행 범위를 명시한다.
- 임의 demo 자료는 is_mock/data_mode 등으로 명확히 표시한다. 출처/날짜가 없는 실제 자료를 가짜 검증일·좌표·판매 상태로 보충하지 않는다.
- 승인된 행신 자료는 8매장/57옵션의 staging 비교 자료다. 현재 판매·좌표·검증일이 부족하므로 기존 운영 Repository에 맞추기 위해 사실을 꾸미지 않는다. 활용 시 staging 전용 어댑터/표시 계약을 따로 정한다.
- 코드에 DB명/키를 박아 넣지 않는다. 읽기 전용 계정/풀·파라미터 바인딩·쿼리 제한을 사용하고 오류를 빈 결과로 바꾸지 않는다.
- 실제 RDS/원본 데이터 쓰기는 별도 작업이다. 이번 계획 작성은 실제 DB 초기화·접속·볼륨 삭제의 실행 승인이 아니다.

## 4. 일정에 따른 실행 순서

아래는 11/10~11/13 목표 순서이며 확정된 팀 일정이 아니다. 단계가 끝나지 않으면 다음 단계의 완료를 주장하지 않는다. 하나씩 구현하고 결과를 확인한다.

| 단계 | 권장 시점 | 산출물/변경 범위 | 완료 기준 |
|---|---|---|---|
| A 계약·데이터 결정 | 11/10 | DTO·대표 요청/정답·demo/mock 범위, 프런트 합의 | 정확한 메뉴/옵션·필수/미지원 조건과 데이터 모드 명시 |
| B DB 검색 세로 연결 | 11/10~11/11 | backend 설정·Repository 팩토리·서비스, 격리 seed/cleanup안 | 칩 입력→검증→조회→정렬→카드. 0 LLM, 모의 SQL 및 승인된 격리 DB 검증 구분 |
| C Gemini 자연어 연결 | 11/11 | extraction/contracts/service, 확인 흐름 | 모의 제공자 테스트 후 소량 승인된 실제 호출. 추출 실패 시 자동 조건 완화 없음 |
| D 이유·태그·앱 계약 연결 | 11/11~11/12 | 서버 템플릿과 담당자 합의된 API/화면 | 동일 조건의 칩/자연어 결과 일치, 출처·예시 표시 유지 |
| E 시연 점검·백업 | 11/12 | 재현 스크립트/노트북·시연 절차·녹화 | 호출 실패/빈 결과/재시도 안내, APK/mock·로컬·AWS 구분 |
| 발표 | 11/13 | 검증된 경로만 시연 | 준비 안 된 Gemini/DB 연결은 mock 결과로 표시, 실제 연동 성공으로 설명하지 않음 |

시간이 부족하면 C 이후 확장을 멈추고 B의 칩 기반 검색을 우선 안정화한다. 실제 Gemini 장애 시 칩 입력으로 전환할 수 있게 하되, 자연어를 해석한 것처럼 대체하지 않는다. DB 실패를 실제 검색 성공처럼 보이는 mock으로 조용히 바꾸지 않는다. 선택 확장인 LLM 이유 문장·평점/목적 추천·Agent 통합은 미룬다.

## 5. 공통 작업 프롬프트

아래 공통 프롬프트와 해당 단계 프롬프트를 함께 사용한다.

```text
docs/midterm-ai-mvp-plan.md와 현재 코드·README·ERD를 먼저 확인하라.
이번 목표는 발표용 칩/자연어→Express→DB 검색·추천이며 Python Agent는 실행 경로에 넣지 않는다.
선택한 단계 하나만 수행하고 변경 파일·목적·검증 방법을 먼저 설명하라.
기존 modules 구조·HTTP 계약·프런트 담당자의 로그인/지도/탭을 보존하고, 계약 변경은 명시하라.
Gemini는 조건 제안만 하고 서버가 바인딩 SQL로 후보·가격·순위를 결정하게 하라.
기본은 mock/주입 테스트다. 실제 API/DB 실행 전 대상·모드·횟수·예산이 명시돼 있는지 확인하라.
행신 staging을 현재 판매 자료로 둔갑시키거나 없는 태그/좌표/확인일을 생성하지 마라.
공개 운영 차단을 일정 때문에 해제하지 마라. Git/배포/실제 DB 쓰기는 별도 지시 없이 실행하지 마라.
단계 종료 시 변경 파일, 실제 검증 결과, 데이터/API 호출 범위, 미완료·다음 조건을 보고하라.
```

### A — 계약·입력 범위

```text
A단계를 수행하라. 현재 프런트와 prepare/confirm/직접 검색 DTO를 비교해 칩/자연어 공통 조건을 설계하라.
menu_id 또는 표준 메뉴 코드, HOT/ICE·사이즈, 예산·가격순과 미지원 조건을 구분하라.
현재 category를 정확한 메뉴명으로 오인하지 마라. 자연어 추출 근거와 UI 기본값도 구분하라.
자료가 없거나 팀 합의 전인 필드는 결정 목록으로 남기고 대표 입력/정답 fixture를 작성하라.
DB/LLM/프런트 구조를 실제 변경하지 말고 현재/목표 계약 차이를 보고하라.
```

### B — 구조화 조건으로 DB 검색

```text
B단계를 수행하라. 합의된 스키마와 demo/mock 모드로 Repository 팩토리·풀 주입을 연결하라.
운영 스키마와 staging을 구분하고 환경 설정에서 명시적으로 데이터 모드를 선택하게 하라.
먼저 SQL 실행기를 주입해 가격 경계/메뉴·옵션/판매 상태/정렬 동률/빈 결과/DB 오류를 검증하라.
실제 격리 DB 검증은 대상과 실행 지시가 있을 때만 수행하라. 칩 경로는 LLM 0회여야 한다.
모든 SQL을 모델에 생성시키지 말고 허용 조건과 바인딩 값으로만 검색하라.
```

### C — 자연어 조건 추출

```text
C단계를 수행하라. Gemini가 공통 DTO에 맞는 미확정 조건·원문 근거·미지원 항목을 반환하게 하라.
확정 전 표시/수정·확인, 누락 위치 재준비, 조건 완화 금지를 유지하라.
가격/메뉴/온도 누락·복수 메뉴·충돌·미지원 목적·프롬프트 주입·잘못된 출력·429/503/시간 초과를
모의 응답으로 검증하라. 1회 자연어 추출의 기본 모델 요청은 1회, 자동 무한 재시도는 금지한다.
실제 호출은 별도 확정된 모델/대표 문장/횟수 상한으로 실행하고 실패도 결과에 기록하라.
Gemini 실패를 임의 정규식 해석 성공으로 대체하지 말고 칩 입력 전환을 안내하라.
```

### D — 이유·태그·프런트 연결

```text
D단계를 수행하라. DB의 후보 ID·가격·메뉴·출처와 충족한 조건으로 서버 이유/태그를 구성하라.
임시 자료는 예시라고 표시하고 조용함·공부 적합·최신 가격 등 없는 사실은 쓰지 마라.
먼저 템플릿을 사용하고 Gemini 이유 생성은 필요성이 확인된 선택 기능으로 분리하라.
추가 모델 출력도 없는 후보 ID/가격/속성을 반영하지 말고 실패 시 검증된 템플릿으로 돌아가라.
프런트 담당자와 계약한 범위만 통합하고 문자열/숫자 매장 ID·Kakao ID·메뉴 분류 차이를 확인하라.
화면 전체 덮어쓰기나 중복 추천 화면 추가 없이 타입/API·렌더 테스트를 실행하라.
```

### E — 발표 재현·실패 대응

```text
E단계를 수행하라. 칩/자연어가 같은 확정 조건일 때 후보 ID·가격·순서가 같은지 확인하라.
대표 성공/빈 결과/지원 불가/제공자 실패/DB 실패를 포함한 재현 스크립트 또는 모의 노트북을 준비하라.
실제 데이터 노트북은 명시적 실행 선택을 유지하고 출력·키·실제 좌표를 저장하지 마라.
지정 환경에서 검증한 경우에만 에뮬레이터·실제 API·DB·AWS 성공으로 기록하라.
mock APK+녹화/고정 fixture 백업을 유지하고 시연 중 실제 연결 실패를 mock 성공으로 숨기지 마라.
```

## 6. 통과 기준과 공개 배포 경계

- 필수 조건 위반 후보 0건, 정확한 메뉴/옵션/가격의 DB 값 사용, 미지원 조건 보존.
- 칩 경로 모델 호출 0회. 자연어 추출은 기본 1회. 템플릿 이유는 추가 호출 0회. 모델 이유 확장 시 최대 1회 추가로 별도 집계.
- 이하/미만, 정확한 상한, NULL·SOLD_OUT·미검증 출처, 동률, 빈 결과, LLM/DB 오류 테스트.
- 요청 수·지연·오류는 기록하되 키·사용자 원문·위치·토큰은 로그에서 제외.
- 자연어 소량 실호출은 예를 들어 대표 5문장, 총 5회 상한의 계획을 먼저 합의한다. 이 예시는 현재 승인된 호출 예산이 아니다. 모델 ID·지원 범위/할당량은 실제 평가 시 공식 정보와 계정에서 확인한다.
- 로컬 개발 시연과 ALB 공개 배포를 구분한다. 현재 인증/공유 제한이 미완료이므로 production 503은 유지한다. 키를 앱에 넣거나 익명 공개 Gemini 경로를 만들어 우회하지 않는다.
- 공개 서비스는 인증·사용자별 공유 제한/소유권·HTTPS·DB/TLS·이미지/다중 서버 검증 후 활성화한다. 기존 mock APK와 AWS health 분리 시연은 유지 가능하다.

## 7. 다음 작업의 시작점

### 실제 HTTP 통합 검증 완료 (2026-11-10)

사용자 진행 요청에 따라 .env 모델 gemini-3.5-flash-lite, Gemini 최대 1회/재시도 없음으로 로컬 127.0.0.1 임시 서버에서 검증했다. prepare 요청(4천 원 이하 아이스 아메리카노)은 HTTP 200/AWAITING_CONFIRMATION, 정확한 메뉴·온도·4000원 상한을 반환했다. 반환된 전체 조건을 명시적으로 confirmed=true로 보내 confirm한 결과 HTTP 200/RESULT, mock 자료 demo-1 3000원·demo-3 4000원이 가격순으로 반환됐다. confirm 모델 호출 0회, 총 외부 호출 1회, 준비 2123ms/전체 2126ms. 키·제안 토큰은 출력하지 않았고 임시 서버는 종료했다.

이로써 로컬 HTTP→실제 Gemini 조건 추출→확인→모의 검색의 단일 정상 흐름을 확인했다. 실제 DB/프런트/공개 배포/인증·공유 상태 통합 성공은 아니다. 실제 추출 평가 10회와 이번 통합 1회를 합친 누적 호출은 11회다. 다음은 DB 파일 수신 시 스키마/필드 대조·Repository 연결 준비, 프런트 브랜치 통합 계약 확인이다. 추가 외부 API·Git 작업은 사용자 확인 후 진행한다.

최신 진행: MVP HTTP prepare에 EXTRACTION_MODE 공급자 선택 연결 완료. search/confirm은 LLM 없이 모의 자료 검색. 전체 백엔드 테스트 28개와 빌드 통과, 외부 요청은 모두 주입 응답으로 검증했으며 실제 호출은 0회. 기존 API·기본 mock·production 차단 유지. 아래의 HTTP mock 고정 설명은 이전 단계 기록이다. 다음은 승인된 예산 내 로컬 실제 HTTP prepare→confirm 통합 검증이며 DB 파일 수신은 별도 대기한다.

### 실제 Gemini 2차 재평가 결과 (2026-11-10)

사용자 재평가 요청으로 동일 .env 모델 gemini-3.5-flash-lite에 수정 프롬프트로 5회 호출했다. 자동 재시도 0회, 실제 DB/Git 작업 0회. 1·2차 합산 실제 호출은 10회다.

|---|---|---|---|
| 4천 원 이하 아이스 아메리카노 | 일치 | 없음: 정상 | 1734 |

조건 필드 및 미해결 존재 여부 판정 5/5 통과(1차 2/5에서 개선). 미해결 문자열도 검토하여 해당 미지원 의미 보존을 확인했다. 지연 866~2863ms, 평균 약 1622ms. 정상 추천 표현·가격순을 미지원으로 처리하던 문제는 이 표본에서 해소됐다.

소량 동일 문장 재평가이므로 전체 표현의 일반화·운영 품질을 입증하지 않는다. 현재 실행기는 자연어 추출만 평가하며 실제 DB 조회·프런트·HTTP 실모델 연결 검증은 아니다. HTTP는 여전히 mock이다. 다음은 설정 기반 공급자 선택과 HTTP 통합을 모의 테스트한 뒤 승인 범위에서 로컬 실호출을 검증하는 작업이다.

### 실제 Gemini 1차 평가 결과 (2026-11-10)

사용자가 현재 .env 모델·최대 5회·재시도 없음을 승인해 실행했다. 모델 gemini-3.5-flash-lite, 실제 요청 5회/추가 재시도 0회, 실제 DB 호출 0회. 실행기 `backend/scripts/evaluate-midterm.cjs`는 기본 dry-run이며 `--live`는 별도 승인 후 실행한다. 키·제공자 원문 오류는 출력하지 않는다.

| 대표 입력 | 조건 필드 | 미해결 판정 | 시간(ms) |

조건값 5/5 일치, 미해결 존재 여부까지 포함한 단순 판정 2/5. 이는 소표본 실제 추출 평가이며 DB 검색·앱 통합/전체 의미 정확도 통과를 의미하지 않는다. 공급자 오류는 없었다.

정상 요청이 확인 단계에서 막히는 과도한 unresolved를 개선하기 위해 추천 요청 표현·가격순은 지원 항목이며 미해결에 넣지 말라는 지시를 추가했다. 이후 빌드와 관련 모의 테스트 5개 통과. 수정 프롬프트의 실제 품질은 재호출하지 않아 미확인이다. 추가 실제 호출은 새 승인 후 수행한다. HTTP 경로는 여전히 mock이므로 현재 .env 모델 설정만으로 실제 연결이 활성화된 것은 아니다.

Gemini 어댑터 준비 완료: 명시 설정/주입 가능한 요청 함수·JSON/종료 검사·오류 처리 구현. 실제 외부 호출 없이 신규 2개 포함 관련 테스트 5개와 빌드 통과. HTTP는 mock 유지. 다음 실호출 전 사용할 모델 ID와 총 요청 상한(권장 대표 문장 5개, 무재시도)을 확인한다. 실제 모델 품질·DB 연결 성공은 아직 주장하지 않는다.

새 DTO의 개발용 `/api/recommendations/mvp/search·prepare·confirm` 연결 완료. 모의 공급자 추출·서명 확인·검색을 통합했고 빌드 및 전체 백엔드 25개 테스트 통과. 기존 API 유지, 프런트 미변경, production 차단 유지. 실제 Gemini 어댑터와 모델/호출 예산은 미확정·미실행, DB 파일 수신 후 어댑터 연결 예정. 자세한 요청 계약은 [MVP 계약](midterm-recommendation-contract.md) 참조.

B단계 준비 진행: midterm.ts 공통 검증/비동기 저장소 인터페이스/모의 옵션 검색·이유·태그 구현. 빌드와 신규 모의 테스트 3개 통과. 실제 DB 파일 수신·스키마 매핑·풀/팩토리·HTTP 연결은 미완료다. 다음은 기존 API와 새 DTO의 호환 연결 및 모의 제공자 기반 자연어 추출 준비이며 실제 외부 호출/Git은 사용자 확인 전 수행하지 않는다.

A단계 진행: [입력·데이터 계약 초안](midterm-recommendation-contract.md)과 대표 입력/정답 fixture 5개 작성. 현재 HTTP 계약은 변경하지 않았다. 프런트 브랜치·담당자 DB 파일 도착 시 이 계약과 대조한다. 실제 모델 평가·DB 조회는 미실행이며 다음은 B단계의 mock 검색/검증기 연결이다. 외부 API·Git 작업은 사용자 확인 후 수행한다.

우선 A단계에서 정확한 메뉴·옵션과 데이터 모드를 확정한다. DB 스키마가 아직 준비되지 않았다면 작은 fixture와 주입 SQL 테스트로 B까지 준비하고, 이후 승인된 격리 DB에 연결한다. 실제 데이터가 갖춰지기 전 동작 결과를 실매장 추천으로 표시하지 않는다.

장기 과제(리뷰 Agent 실모델/DB/스케줄러·리뷰 특징 순위·분산 작업)는 계속 보존하지만 이번 MVP의 필수 실행 의존성으로 추가하지 않는다. 화면·데이터·인증 담당자와 필요한 계약만 우선 조율한다. 원격 이슈/PR/댓글 수정은 별도 지시 전 하지 않는다.
