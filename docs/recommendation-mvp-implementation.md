# 추천 탭 DB 연동 MVP 구현 기준

기준: 2026-11-11 `develop` 코드와 `산학프로젝트/최신 문서`의 API 명세서, 기능 명세서 F06, 요구사항 분석서 FR-20~23. 이 문서는 구현 계획이며 완료된 API를 뜻하지 않는다.

## 목표와 흐름

- 조건 칩만 선택: 구조화 조건 검증 → DB 후보 조회 → 서버에서 필터·순위 결정 → 결과 반환. 자연어 추출 호출은 0회다.
- 자연어 입력: Gemini가 조건을 구조화 → 근거와 미해결 조건 표시 → 사용자 확인 또는 추가 질문 → 동일한 DB 검색 함수로 조회한다. 모델은 SQL, 가격, 매장, 순위를 생성하지 않는다.
- 최신 기능 명세서 F06은 상위 3곳의 DB 사실로 Gemini 추천 이유를 만들고, AI 실패 시 태그 기반 기본 문구를 쓰도록 한다. DB 검색 MVP는 먼저 서버 템플릿 이유로 완성하고, Gemini 이유 생성은 후속 단계로 분리한다. 칩 경로의 자연어 **추출** 호출은 0회다.

## 최신 문서의 계약

API 명세서 초안의 Base URL은 `/api/v1`이다. `POST /recommendations`는 `lat`, `lng`, `budget` (`UNDER_3000|UNDER_5000|ANY`), `purpose` (`TAKEOUT|STUDY|TALK|DRIVE_THRU`), `tastes` (`LOW_ACIDITY|NUTTY|SWEET|DECAF|MILK`), `distance` (`WALK_5|WALK_10|CAR_10`)를 받는다. 응답은 `conditions`와 순위·매장 ID·거리·메뉴·가격·평점·태그·이유를 담은 `results`다. `POST /recommendations/chat`은 `message`, 위치, 이전 `context`를 받고 조건 부족 시 `QUESTION`, 충분할 때 `RESULT`를 반환한다. 두 경로는 검색·순위 구현을 공유한다. 인증은 USER로 정의돼 있다.

## 현재 코드와 연결 작업

| 영역 | 현재 상태 | MVP 작업 |
| --- | --- | --- |
| 추천 탭 | `RecommendScreen`이 `budget/purposes/tastes/travelMinutes/travelMode/query`를 전달 | 명세의 단일 `purpose`, enum 값과 위치 정책을 정해 변환. 지원하지 않는 조건은 조용히 제거하지 않기 |
| 결과 화면 | `/api/recommendations`에 화면 DTO를 직접 보내 `items/mode`를 기대 | 서버 요청·응답 계약을 통일하고 빈 결과·오류·가격 출처를 표시 |
| Express | 일반 추천 경로는 기본 모의 Repository, 별도 `/mvp/search·prepare·confirm`은 제한된 메뉴·가격 검색 | 공통 DB 검색 서비스 구축 후 칩·자연어 경로가 재사용. 개발용 MVP 경로는 필요한 로직만 재사용하고 제품 계약과 혼동하지 않기 |

| 운영 | 추천 라우터는 인증·공유 호출 제한 전까지 production에서 503 | 개발 환경에서 검증 후 인증·사용자별 제한·다중 서버 상태를 연결할 때 운영 활성화 |

## 데이터에 따른 MVP 범위

현재 스키마로 검증 가능한 조건은 가격, 좌표, 드라이브스루, 디카페인, 우유 포함 여부다. 평점·리뷰 수는 저장 필드가 있지만 현재 데이터의 신뢰도를 확인해야 한다. `WALK_5/10`, `CAR_10`은 좌표만으로 실제 이동 시간을 보장하지 않으므로 길찾기 자료가 없으면 시간 조건으로 단정하지 않는다.

조용함·콘센트·산미·고소함·단맛은 추후 리뷰를 통해 수집한다. 수집·검증 전에는 해당 태그를 근거 없이 필터나 이유에 사용하지 않는다. 공부·작업/대화 적합성도 별도 근거가 필요하다. 기존 화면의 기본값에 있는 `공부·작업`, `산미 적은`은 사용자에게 이미 충족된 조건처럼 표시하지 않도록 MVP 화면에서 처리한다.

## 구현 순서와 검증 기준

1. 화면·서버 공통 조건/결과 DTO를 확정한다. 최신 API 명세서의 `/api/v1`, `error` 형식과 현재 `/api`, `message` 형식 차이도 정리한다.
2. DB 검색을 연결하고 확정 조건의 칩 경로를 완성한다. 정상 빈 결과와 DB 장애를 구분한다.
3. Gemini 추출 결과를 검증하고 원문 근거·미지원 조건을 사용자에게 보여준 뒤 확정 조건으로 같은 검색 함수를 호출한다.
4. 결과 카드에 실제 일치한 메뉴·가격 옵션, 출처, 거리 근거를 표시한다. DB 사실에 없는 추천 이유는 허용하지 않는다.
5. 테스트: 칩만 사용하면 자연어 추출 0회; 동일 확정 조건의 칩·자연어 후보 ID/가격/순서 일치; 미지원 조건·위치 부재·DB 장애·Gemini 장애·빈 결과 구분; DEMO 가격을 실제 검증 가격으로 표시하지 않음.

## 확정한 구현 방향

아래는 최신 문서의 제품 목표를 현재 코드에서 구현하기 위한 **개발 단계 결정**이다. 명세를 이미 구현했다고 주장하지 않는다.

1. 먼저 현재 앱과 Express가 사용하는 `/api/recommendations` 및 공통 `success/data/message` 응답을 연결한다. `/api/v1`과 `success/data/error`로 바꾸는 일은 팀 전체 API 버전 전환 때 한 번에 수행한다. 개발용 `/mvp/*`는 회귀 실험 경로로 유지하고 제품 화면에서 호출하지 않는다.
2. 두 입력 방식은 **하나의 `searchRecommendations(confirmedConditions)`**를 사용한다. 칩은 바로 검색한다. 자연어는 Gemini 추출 → 제안 조건·원문 근거·미해결 항목 표시 → 명시적 확인 → 검색으로 간다. 자연어가 비어 있으면 추출기를 호출하지 않는다.
3. 이유 생성은 별도 단계다. DB 검색 MVP에서는 DB 필드만 사용한 서버 템플릿 이유를 반환한다. 이후 F06 명세에 따라 상위 3개 후보의 제한된 DB 사실로 Gemini 이유를 만들고, 응답의 가격·매장·태그 주장을 서버가 검증한다. 이유 생성 실패 시 DB 기반 문구로 유지한다. 따라서 최종 F06 구현에서는 칩 요청에도 이유 생성용 호출이 있을 수 있다. 사용자의 “자연어 미입력 시 DB에서 바로 반환”은 **검색 경로에서 자연어 추출을 생략**하는 것으로 해석하며, 이유 생성 사용 여부는 UI와 API에 별도 표시한다.
4. 로그인과 공유 호출 제한이 없는 현재 production 503 차단을 유지한다. 개발용 DB 시연 완료를 운영 배포 완료로 표시하지 않는다.

## MVP 입력 계약과 조건별 판정

앱에서는 기존 `RecommendationRequest`를 API 전송용 DTO로 그대로 보내지 않고 변환한다. 서버는 enum, 수치, 문자열 길이, 중복/충돌을 검증하며 모르는 필드를 거절한다. ID는 JS 숫자로 반올림하지 않도록 문자열을 유지한다.

| 화면 조건 | DB 근거 / 처리 | MVP 화면 정책 |
| --- | --- | --- |
| 예산 3천/5천/제한 없음 | `menu_prices.price <= maxPrice`, 판매 중 옵션만 | 즉시 검색 가능 |
| 드라이브스루 | `cafes.has_drive_thru` | 즉시 검색 가능 |
| 디카페인·우유 포함 | `menus.is_decaf`, `menus.has_milk` | 해당 메뉴 가격 데이터가 존재할 때만 일치로 판단. 빈 결과는 정상 빈 결과 |
| 테이크아웃 | 현재 매장별 지원 여부 컬럼 없음 | 충족을 주장하지 않음. 선택 시 미지원 안내 |
| 공부·작업·대화, 산미 적은·고소한·달달한 | 향후 리뷰 분석·태그 근거 필요 | 현재 기본 선택을 제거하고 비활성/준비 중으로 표시. 요청에 들어오면 422 또는 명시적 미해결 제안 |
| 도보/차로 5·10분 | 좌표만으로 실제 경로 이동시간 판단 불가 | 시간 칩을 정확한 필터로 사용하지 않음. MVP에서 좌표 기반 **직선 반경**을 별도 명칭·단위로 제공하거나 시간 칩은 준비 중으로 표시 |
| 자연어에만 있는 정확한 메뉴·온도·사이즈 | 기존 `/mvp` 추출/DB 검색 일부 재사용 가능 | 칩·자연어의 최종 조건 DTO에 포함하고 실제 가격 옵션과 대조 |

결과의 매장과 가격은 실제 조회 행에서만 만든다. `DEMO` 자료는 화면에 ‘시연 가격·확인일 미확인’으로 표시하고 실제 판매·가격 확인일을 보장하지 않는다. 평점과 리뷰 수는 값의 출처·신뢰도를 확인하기 전 순위 근거로 쓰지 않는다. 초기 순위는 충족 조건 확인 후 가격 오름차순, 거리, 가격 옵션 ID 순의 결정적 정렬로 시작한다. 매장별 대표 가격은 필터에 일치한 옵션에서 선택하고 같은 매장을 중복 카드로 만들지 않는다.

## 작업 단위와 완료 조건

| 단계 | 변경 대상 | 완료 조건 |
| --- | --- | --- |
| 1. 계약·화면 정리 | `frontend/src/app/domain.ts`, 추천 화면/결과 화면, API 타입; 백엔드 입력 검증 | 지원/미지원 칩과 기본값이 명확하고 프런트·서버 DTO가 일치. 미지원 조건의 무음 제거 없음 |
| 2. DB 검색 | `backend/src/modules/recommendations/`의 서비스·Repository·라우터 | 제한된 후보 조회, 필수 조건 필터, 가격순 정렬, 실제 가격 옵션/출처 반환. 파라미터 바인딩, 빈 결과 200과 DB 장애 503 구분 |
| 3. 칩 경로 통합 | `RecommendScreen` → API → `RecommendationResultScreen` | 자연어 공란에서 Gemini 추출 0회. 로딩·재시도·빈 결과·시연 가격 안내, 카페 ID로 상세/길찾기 연결 |
| 4. 자연어 경로 | Gemini 추출·제안 검증·확인 UI·공통 검색 | 제안의 근거와 미해결 조건 표시. 사용자 확인 전 검색하지 않음. 동일 확정 조건이면 칩 경로와 동일한 후보·가격·순위 |
| 5. 이유 생성 | 제한된 DB 사실 전달·출력 검증·기본 문구 | 가격·이벤트·태그를 발명한 문장은 폐기. Gemini 장애 때 검색 결과 유지, 호출 횟수와 오류를 구분 |
| 6. 운영 준비 | 인증·사용자 소유권·공유 호출 제한·배포 | 두 서버에서 제한/확인 상태가 일관되고 실제 DB·기기 검증이 끝난 뒤 별도 운영 활성화 결정 |

각 단계의 테스트는 경계와 실패 경로를 검증한다. 2단계에는 예산 경계(3천·5천), 품절/DEMO/출처, 동일 매장 여러 옵션, BIGINT ID, 위치 없는 요청, DB 장애가 포함된다. 4단계에는 단일 Gemini 호출, 모순·미지원 요청, 제안 만료/변조, 수정 조건 확인을 포함한다. 실제 Gemini·실제 DB·Android 기기 검증은 모의 테스트와 별도로 기록한다. 작업 순서는 1→2→3→4→5→6이며 3단계가 끝나면 칩 기반 DB MVP를 시연할 수 있다.

참고 원문: `최신 문서/커피 주유소 · API 명세서` 2.3 및 `POST /recommendations`, `최신 문서/커피 주유소 · 기능 명세서` F06, `최신 문서/커피 주유소 · 요구사항 분석서` FR-20~23. 저장소의 `docs/api.md`, `docs/ai-recommendation.md`, `docs/midterm-recommendation-contract.md`는 현재 구현 안내이며 최신 문서의 제품 계약과 구분한다.

1~5단계는 코드·주입 테스트 수준에서 연결됐다. 전체 백엔드 42개, 프런트 199개 테스트가 통과했다. 2026-11-11 후속 실제 검증에서 중지돼 있던 기존 `coffee-mysql` 컨테이너를 시작했고, 테이블이 없는 `coffee_station`에 공식 `schema.sql`과 `seeds/haengsin.sql`을 적용했다(8매장, 2메뉴, 55가격). 시연 가격 기준 예산 5천 원 이하와 우유 포함은 각각 상위 3건, 디카페인과 드라이브스루는 정상 빈 결과였다. 사용자는 MVP에서 이 빈 결과를 유지하기로 했다. 칩 HTTP 검색 200/3건, mock 자연어 준비 200→확인 200/빈 결과를 확인했다. 실제 Gemini 조건 추출은 대표 문장 `5천 원 이하 디카페인 메뉴를 찾아줘`에서 첫 호출의 불필요한 `메뉴` 미해결 판정을 프롬프트 수정 후 재호출하여 `AWAITING_CONFIRMATION`으로 확인했다. 사용자 승인 후 실제 Gemini 이유 선택 1회에서 DB 시연 후보 3건의 직선거리 문구가 선택됐다. Android 화면은 미검증이다. 6단계는 현재 저장소에 인증 구현과 공유 저장소가 없으므로 완료로 표시하지 않는다.
